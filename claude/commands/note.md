
@~/vault/notes 配下にノートを作ります。

以下の指示に従ってください。

## 1. 見出し構成を確認する

ノートを作る前に、ファイル名と、見出しの構成と各見出しにどのような内容を書くかをまず先に考え、それをユーザーに提示してフィードバックをもらう。ユーザーがその構成と内容で作っていいと許可してから、ノートを作り始める。ただし、「見出しの確認はスキップしてください」など、明確にフィードバックの工程をスキップする指示があったときは、そのままノートの作成に進んでください。

**【重要】見出しは短く簡潔にしてください。**

目安は全角 12〜13 文字以内です。次の2つのパターンに当てはまっていないか、見出しを提示する前に必ず確認してください。

- 動詞の目的語に説明的な修飾語を付けている
    - ❌「保存されている設定を変更する」→ ✅「設定を変更する」
- 見出し自体が完全な一文の説明になっている
    - ❌「ボタンを押すと自動で保存される」→ ✅「自動保存の仕組み」

```
ファイル名

1. セクション1
   1-1. サブセクション
    - 内容
   1-2. サブセクション
    - 内容
    callout: 補足的内容
2. セクション2
   2-1. サブセクション
    - 内容
...
```

また、見出し構成を組み立てるときは「情報の粒度と重要性」を気にしてください。

異なる粒度の内容や、本当に重要な情報と些末な情報を同じレイヤーの見出しにしないでください。本筋とは関係ない些末な情報は Callout で書いてください。

## 2. ファイルの雛形を作る

### 2-1. ファイル名

`YYMMdd_タイトル.md` の形式。スペースは使わず、必要なら `_` や `-` で繋ぐ。 @~/vault/notes/MOC.md も参考にする。タイトルも基本的にはなるべく短く簡潔にする。

例: `260810_Dockerの仕組み.md`

### 2-2. frontmatter

ノートの frontmatter には現在のセッション情報を記録する。新規ノート作成時だけでなく、既存ノートを編集するときも、現在のセッション情報がまだ記録されていなければ `-` で追記する。

```
---
resume_cmd:
  - claude --resume {セッションAのID}
  - claude --resume {セッションBのID}
session_cwd:
  - {セッションAが開始されたディレクトリ}
  - {セッションBが開始されたディレクトリ}
---
```

- セッションID
    - システムプロンプトの「Scratchpad Directory」のパスから UUID 部分（末尾から2番目のセグメント）を取る。
- session_cwd
    - システムプロンプトの「Primary working directory」の値。ホームディレクトリのパス（`/Users/<ユーザー名>`）は `~` に変換する。
    - すでに同じディレクトリが存在する場合は省略する

### 2-3. 目次と見出し

frontmatter の直後に、一行も空けずに次のように書く。マーカーの間は Auto TOC プラグインにより "編集時" には自動生成されるが、 "作成時" は自動生成されないので、内容に合わせて見出しへのリンクを箇条書きで書く。

```
**目次**：
%% toc-start %%
- [[#1. 最初のセクション]]
    - [[#1-1. サブセクション]]
- [[#2. 次のセクション]]
%% toc-end %%
```

- 本文は必ず `## 1. ...` から始める。それより前に導入文を書かない
- 中見出しは「1.」「2.」、小見出しは「1-1.」「1-2.」と番号を振る

## 3. MOC の更新する

作成したら @~/vault/notes/MOC.md の **「## 新しいノート」セクション** の先頭に `[[ファイル名]]` を追加する。内容から置き場所を勝手に決めない。

## 4. 本文を書く

### 4-1. 絶対ルール

- 日本語・ですます調でかく。
- 学んだことや理解したことを整理し、あとから読み返すためのノートであることを意識する。
- そのテーマや周辺知識についてわかっていない初心者・初学者に向けて書くイメージで、平易な文章で、スラスラ読めるようにかく。
- 中学生でもわかるようにわかりやすく書く。
- 読者は、このノートが作られたときの会話を知らない第三者だと考えて書く。
- 基本的に他のノートを参照しない。ただし、内容が多く重複する、または強く関連していてリンクを貼ることが好ましいと判断したときはユーザーに相談する。

### 4-2. 段落とスペースについて

- 半角の英字と全角日本語の間にはスペースを入れる
- 段落の間には空行（2回の改行）を入れる
- 1段落あたりの文字数はなるべく少なくする

### 4-3. 太字について

- **太字** にする単語の外側（前と後）には必ず半角スペースを入れる。内側にはスペースを入れない
    - ✅ これは **重要** です
    - ❌ これは**重要**です、これは ** 重要 ** です
- カギ括弧を太字で強調したいときは、カギ括弧の外側に ** ** をつける
    - ✅  これは **「重要」** です
    - ❌  これは「 **重要** 」です

### 4-4. 箇条書きについて

- 基本的には普通の文章で流れのある説明を基本とし、AIにありがちな本文の大部分を箇条書きで構成しない
- 箇条書きは同じ粒度のアイテムを並列で述べるときに使う
- 順序があるときは番号付きリスト
- ラベル（立項）と説明文を同じ行に詰め込まず、必ずインデントされた箇条書きで説明をつける。

❌ 悪い例:
```
- **`assets/`** — 画像の保存先。設定で変更する必要がある。
```

✅ 良い例:
```
- **`assets/`**
    - 画像の保存先
    - 設定で変更する必要がある
```

### 4-5. 技術用語について

- 初出の重要な技術用語は **太字** にする
    - 2回目以降は繰り返し太字にしない
- 略語やコマンド、難しめの英語には初出時に正式名称や由来・意味を解説する。
    - 例: `ls` は "list"（リスト）が由来です。
    - 例：UTI は「Uniform Type Identifier」の略で「統一された型の識別子」という意味です。
- 固有名詞も、読者が知らない可能性があるなら同様に扱う。

## 5. Obsidianについて

このノートは Obsidian というマークダウン編集ツールで閲覧・修正します。

そのうえで次の2点に注意してください。

### 5-1. Calloutの活用

補足には、まず `memo` を使う。灰色の枠だけのカスタム Callout で、色が付かないぶん本文の流れを壊さない。

```
> [!memo] **タイトル**
> 本文
```

タイトルは「ですます調」でかかない。
タイトルが不要なときは `|nt` を付ける。枠だけになる。

```
> [!memo|nt]
> 本文
```

「ちなみに」で始まるような、本筋から少し外れる内容は本文に置かず、この Callout に出す。

コールアウト内でもコードブロックは使用することができる。

```
> [!memo] **タイトル**
> 本文
> ```ruby
> コードブロック
> ```
```

注意点や警告など、色を付けて目立たせる必要があるものだけ、下の表から型を選ぶ。色付きの Callout は数が増えると本文の重要な箇所が埋もれるため、1 つのノートに何度も使わない。

なお、本文の一部を目立たせる目的で Callout を使ってはいけない。その場合は太字を使う。

また **Callout 内にテーブルを入れてはいけない**。これは Confluence 同期時にパースエラーになるため。

| 型          | 別名（エイリアス）              | 色    | 用途     |
| ---------- | ---------------------- | ---- | ------ |
| `memo`     | -                      | なし   | 補足・メモ全般 |
| `note`     | -                      | 青    | メモ・補足  |
| `info`     | -                      | 青    | 情報     |
| `todo`     | -                      | 青    | タスク    |
| `abstract` | `summary`, `tldr`      | ティール | 要約     |
| `tip`      | `hint`, `important`    | シアン  | ヒント・コツ |
| `success`  | `check`, `done`        | 緑    | 完了・成功  |
| `question` | `help`, `faq`          | 黄    | 疑問     |
| `warning`  | `caution`, `attention` | オレンジ | 注意     |
| `failure`  | `fail`, `missing`      | 赤    | 失敗     |
| `danger`   | `error`                | 赤    | 危険・重要  |
| `bug`      | -                      | 赤    | バグ     |
| `example`  | -                      | 紫    | 例      |
| `quote`    | `cite`                 | グレー  | 引用     |

### 5-2. Obsidianの特殊記法の注意点

- 以下の記法は Obsidian の特殊記法なので、意図と合わないときは `\` でエスケープする。
    - `[]` → \[\]
    - ページリンク: `[[...]]` → \[\[...\]\] 
    - タグ： `#タグ名` → \#タグ名
    - 画像: `![[...]]` → !\[\[...\]\]
- 次の2つの記法は使わない。
    - ハイライト：`==...==`
    - コメント：`%%...%%`
- テーブル内の縦棒： `|` を使うときは `\|` とエスケープする
    - テーブルの仕切りと解釈されてしまうため

## 6. 追記時の注意点

ノートを作成してから、ユーザーと会話して、修正すべき点や追記すべき点がでてきたときは、局所的にとらえず、必ず全体のバランスを考える。

多くの場合、修正や追記をお願いすると、その部分だけ極端に厚みのある説明になったり、分量が全体とバランスが取れていないことがよくあるので、「このノートにこの記述を足すなら、この場所にこれだけの分量がちょうどいいだろう」という、 **ノート全体の分量のバランス** を常に考える。


## 7.  フィードバック

`/note-fb` などで、作成したノートについてフィードバックがあったときはここに箇条書きで足していく。

- 会話で厚く答えた話題を、そのままの密度でノートに書かない。会話の分量とノートの分量は別に決める。
- 比喩や擬人化で説明を代用しない。何が起きるかをそのまま書く。
    - ❌「エラーを静かに握りつぶします」
    - ✅「エラーが起きても、メッセージを表示せずに処理を続けます」
- 文体の硬さを一定に保つ。説明の途中に話し言葉を混ぜない。
    - ❌「設定をいじると動かなくなります」
    - ✅「設定を変更すると動かなくなります」
- 主語と目的語を省略しない。「何が」「何を」が読み取れる文にする。
    - ❌「この値を変更すると壊れます」
    - ✅「この値を変更すると、アプリが起動しなくなります」
- 見出しを本文の一部として使わない。見出しを読み飛ばしても本文が成立するように書く。
    - ❌ 見出し「インストール方法」→ 本文「これは次のコマンドで行えます。」
    - ✅ 見出し「インストール方法」→ 本文「インストールは次のコマンドで行えます。」
- 並列に並ぶ見出しは、語尾と粒度を揃える。
    - ❌「導入の手順」「設定を変える」
    - ✅「導入する」「設定を変える」
- 見出しは説明的な修飾語や完全な一文にして長くしがちなので、提示前に全角 12〜13 文字以内に収まっているか必ず確認する(詳細は 1 章の見出しルール参照)。
- 構成を提示する前に、各見出しで初めて出る用語がそれ以前で説明済みか確認する。未説明なら順番を入れ替える。入れ替えられないときは「後述の〜」と書く。
- ノートの主題から外れる内容は深追いせず、必要なら別ノートへの分割を提案する。ただし、そのノート単体で内容が完結していることを優先する。
- 末尾に「関連ノート」をまとめて並べない。他のノートへの参照は本文中の自然な流れで置く。
